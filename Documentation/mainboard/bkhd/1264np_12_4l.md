# BKHD 1264NP-12-4L

The BKHD 1264NP-12-4L is an Intel Alder Lake-N (N100) industrial mini-PC
mainboard with an ITE IT8625E Super I/O, four i225/i226 NICs, two SO-DIMM
slots and an M.2 NVMe slot.

## Flashing coreboot

The board uses a 16 MiB SOIC-8 (W25Q128) at the usual location. coreboot is
built without an Intel Flash Descriptor; the existing descriptor/ME are kept
and only the BIOS region is reflashed (internal flashrom works once the
descriptor permissions are right - see "Intel ME" below).

## Board-specific quirks

### Intel ME clobbers the SMMSTORE / EFI variable store

Out of the box the ME has full flash write access (descriptor `FLMSTR2 =
0xffffffff`) and the board's **JME jumper** ("allow ME to program flash")
defaults to *enabled* (pins 2-3). Even though the ME is otherwise neutered,
it **wipes the SMMSTORE region every boot** - so coreboot's CFR runtime
options never apply and the EFI variable store reads back erased (`0xff`),
flooding the log with `EFIVARS: No Firmware Volume header present`.

This is invisible in coreboot's own logs: the ME erases through its own
controller path (no `fast_spi` cycle), so the store is already `0xff` before
coreboot's first read, with no coreboot erase anywhere.

**Fix (either):**

* Hardware: set the **JME jumper to 1-2 (Disable)**, or
* Software (preferred, jumper-independent): deny the ME write access to the
  BIOS region in the descriptor. Surgically patch only `FLMSTR2` (leave
  `FLMSTR1`/host untouched so flashrom still works):

  ```
  # FLMSTR1 @0x80 stays 0xffffffff (host keeps full access)
  # FLMSTR2 @0x84 -> 0x004005ff (ME loses Host/BIOS region write)
  ```

  `ifdtool -l` also works but is too aggressive here - it removes the host's
  BIOS write access too, locking you out of internal flashing.

### Front-panel buzzer (boot beep)

The buzzer is a **passive piezo on GPP_H4** - *not* the legacy PC speaker.
The SoC's SPKR native function lives on GPP_B14, but on this board that pad
is wired to the SATA activity LED, so the PIT/port-0x61 path (and Linux
`pcspkr`) stays silent. The stock AMI firmware bit-bangs GPP_H4 for its POST
beep; coreboot does the same in `beep.c` (`mainboard_boot_beep()` toggles
GPP_H4 with `udelay()` to play an ascending boot chime). Because the buzzer
is passive it must be driven with an AC waveform - setting the GPIO to a
static level makes no sound.

GPP_H4 was identified empirically by sweeping every SoC GPIO output from Linux
with libgpiod and bit-banging each pad until the buzzer responded.

**OS-level beeping** is awkward on this board: a passive buzzer on a plain
GPIO has no standard x86 path. `pcspkr` can't reach it (wrong pad);
`gpio-beeper` only does on/off (silent on a passive buzzer); the only clean
route would be `pwm-gpio` -> `pwm-beeper`, which is bleeding-edge and hard to
wire up via ACPI. The reliable beep is therefore the firmware boot chime.

## Connectors and headers

### CPU_FAN (fan connector)

The fan socket is a **Molex PicoBlade, 1.25 mm pitch, 4-pin** (header part
53261 - mates with PicoBlade housing 51021 + crimp contacts, or a ready-made
PicoBlade cable). It is *not* the usual 2.54 mm PC fan header, so a normal case
fan does not plug in directly.

Pinout (matches the standard 4-pin PWM order and 12 V level):

| Pin | Signal     |
|-----|------------|
| 1   | GND        |
| 2   | +12 V      |
| 3   | FAN_TACH   |
| 4   | FAN_PWM    |

To use an ordinary 4-pin PWM fan, use a *PicoBlade 1.25 mm 4-pin -> 4-pin PWM*
adapter cable (the pin order is 1:1, but verify GND<->GND with a meter first).
PicoBlade contacts are good for ~1 A, which is plenty for a small CPU fan.

### F_USB (internal USB 2.0 header)

A 2x5, 2.54 mm pitch internal USB header (9th pin keyed). Its two USB2 ports
live among the otherwise-empty PCH USB2 ports; enable them in `devicetree.cb`
(`usb2_ports`) to use it. Note that a self-powered add-in (e.g. the USB
Bluetooth of a BCM94360 card wired here) only enumerates if that card has its
own power - the header supplies 5 V VBUS but not a card's 3.3 V rail.

### SATA

One SATA 3.0 connector (separate Data + PWR headers) on a SATA/PCIe **combo
lane = SATA port 1** (`SATAXPCIE1`, GPP_A12 NF1). Being a combo lane it is only
implemented in AHCI when a drive is attached; an empty port reports
`0 ports implemented (port mask 0x0)`, which is expected. The edk2 payload can
boot from an attached SATA drive.

## Working

* Native graphics init (libgfxinit, eDP/HDMI/DP)
* All four NICs, NVMe, USB, SO-DIMM
* IT8625E Super I/O: UART (COM1/COM2), hwmon, user GPIO header
* SMMSTORE / CFR runtime options (with the ME fix above)
* Front-panel boot-beep buzzer (GPP_H4)
